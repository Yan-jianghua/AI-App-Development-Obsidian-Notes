# 数据库、会话与事务

## 请求级会话

常见做法是每个请求获得一个数据库会话，用完关闭。会话不是全局线程安全对象；同步和异步驱动、Session 类型以及连接 URL 必须匹配。

```python
def get_session():
    with Session(engine) as session:
        yield session
```

异步版本使用异步引擎、`AsyncSession` 和 `async with`。不要在 `async def` 中调用长时间阻塞的同步数据库驱动。

## 事务边界

事务应围绕一个完整业务用例，而不是每执行一条 SQL 就提交。成功统一 commit，异常 rollback。唯一性仍由数据库约束保证；“先查不存在再插入”在并发下会竞争。

```text
开始事务 → 读取/锁定必要数据 → 检查业务规则 → 写入 → 提交
                                               异常 → 回滚
```

调用外部 API 与数据库事务不能天然原子。可使用 outbox、状态机、幂等键和补偿操作，而不是让事务一直等待网络。

## ORM 边界与 N+1

ORM 简化映射但不会消除 SQL。列表加载关联对象时可能产生一次主查询加 N 次子查询；用显式预加载、join 或批量查询解决。分页前确认 join 是否造成重复行。

## 迁移

使用迁移工具记录 schema 变化并纳入代码评审。生产迁移优先向后兼容：先添加新列/新表并让新旧代码都能工作，再回填数据、切换读取，最后删除旧结构。大表变更要评估锁和执行时间。

## Repository 与 Service

Repository 表达数据访问，Service 表达业务用例。测试 Service 时可替换 Repository；集成测试再验证 SQL、约束、事务和真实数据库差异。不要制造只转发每个 ORM 方法而无语义的层。

## 常见错误

- 返回响应后才发现懒加载需要已关闭的会话。
- 捕获数据库异常却忘记 rollback，会话保持失败状态。
- 在循环里逐行查询或提交。
- 测试只用 SQLite，却在生产使用 PostgreSQL 并依赖其特性。
- 数据库连接池大于数据库可承受连接数，扩容后雪崩。

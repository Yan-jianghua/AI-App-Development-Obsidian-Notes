# ABAC

## 学完这一篇，你应该会什么

- 能用自己的话解释“ABAC”。
- 知道它在 Python 后端或 AI 应用测试中的作用。
- 能根据下面的例子设计至少一条正常测试和一条失败测试。
- 能识别常见误用，而不是只记住名词。

## 先用白话理解

基于属性的访问控制根据用户、资源、动作和环境属性作决策。

把它看成一个“可验证的工程约定”：先明确输入和前置状态，再执行动作，最后用可观察证据判断结果。证据可以是返回值、异常、数据库状态、工具调用、日志、指标或用户看到的页面。

## 正式定义与边界

在本教材中，**ABAC** 属于“Python 后端与 API 测试”知识域。学习时要同时区分三件事：

1. 它解决的具体问题是什么。
2. 它不解决什么，不能被哪个相似概念替代。
3. 失败时能留下什么可复现的证据。

按请求输入、协议处理、业务逻辑、持久化副作用、响应输出五层设计断言，并覆盖正常、异常、权限和边界路径。

## 具体例子

> 医生只能在值班期间访问其科室患者记录。

可以把这个例子改写成一条最小测试规格：

```text
Given：准备满足前置条件的数据和依赖
When：执行与“ABAC”相关的动作
Then：检查结果、状态和必要副作用
And：再补一个边界或失败路径，确认系统不会悄悄出错
```

### 为什么这个例子有效

它同时说明了“输入是什么、动作是什么、正确证据是什么”。真正落地时，不要只写“运行没有报错”；要把业务承诺转换为明确断言。若结果存在随机性或最终一致性，应使用多次采样、容差、轮询或统计区间，而不是固定等待后凭感觉判断。

## 建议的测试步骤

1. 写出业务规则，并指出谁是调用者、谁是被测对象。
2. 列出正常、边界、异常、权限和并发场景中适用的部分。
3. 准备最小数据，避免无关字段遮挡测试意图。
4. 执行动作，记录版本、配置和外部依赖。
5. 同时断言输出、持久状态和关键副作用。
6. 故意制造一次失败，确认错误信息能帮助定位原因。
7. 把稳定且高价值的用例加入回归套件。

## 常见错误

- 只覆盖“能成功”的快乐路径，没有边界和失败路径。
- 只断言某个函数被调用，却没有验证用户可观察结果。
- 测试依赖真实时间、随机数、网络或共享数据，导致不可重复。
- 把实现细节当成契约，轻微重构就导致大量无意义失败。
- 只断言状态码、不检查响应结构、错误体、数据库变化和权限边界，容易产生“表面通过”的接口测试。

## 最佳实践

- 用业务语言给测试命名，让失败报告直接说明哪条规则被破坏。
- 一个测试集中验证一个行为，但允许为该行为检查多个必要证据。
- 边界值写成表格或参数化用例，避免复制粘贴。
- 对外部系统保留少量真实集成测试，不能只依赖 Mock。
- 对高风险路径保存失败输入、环境和版本，确保能够重放。

## 动手练习

以“医生只能在值班期间访问其科室患者记录。”为背景，写出三条测试：一条正常路径、一条边界路径、一条失败或越权路径。为每条测试写清 Given、When、Then，并指出测试若失败，最可能是哪一层出现问题。

## 面试题

1. 请解释 ABAC，并给出它适用与不适用的场景。
2. 只测正常路径会漏掉什么风险？
3. 你会收集哪些证据来证明这项能力在生产环境中可靠？

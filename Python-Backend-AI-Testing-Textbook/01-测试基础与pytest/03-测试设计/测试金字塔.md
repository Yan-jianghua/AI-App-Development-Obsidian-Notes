# 测试金字塔

## 核心思想

测试金字塔建议底层有大量快速单元测试，中层有适量集成/API 测试，顶部有少量关键 E2E。越靠上越真实，但通常越慢、越贵、越难定位。

```text
        少量 E2E
      适量集成/API
    大量快速单元测试
```

## 为什么这样分布

假设 1000 个输入组合都用浏览器测，套件可能需要数小时且不稳定；同样的业务边界在纯函数测试中几秒即可完成。E2E 保留给“组件装配是否正确”的关键用户旅程。

## 不是固定比例

金字塔是原则，不是必须 70/20/10。数据管道可能需要更多集成测试；简单库可能以单元测试为主；AI 系统还需要评测数据集和线上监控。

## 反模式：冰淇淋筒

大量慢 E2E、少量单元测试会导致反馈慢、失败难定位、团队不信任测试。修复方法是把边界组合和业务规则下沉。

## 如何决定层级

问两个问题：最便宜的哪个层级能发现这个风险？是否需要真实协议/组件才能发现？例如折扣规则用单元测试，SQL 约束用数据库集成，Cookie 登录用 E2E。

## 常见错误

- 只追求单元测试数量，关键集成从未验证。
- 所有测试都访问数据库，反馈过慢。
- 把金字塔当管理 KPI，而不是风险设计方法。

## 练习与面试题

练习：把注册、唯一邮箱、发送邮件、浏览器跳转四类风险分配到合适层级。

面试：测试金字塔为什么不是固定比例公式？

# 回归测试

## 定义

回归测试用于确认代码、配置、依赖、模型或数据变化后，原来正常的能力没有被破坏。

## 典型来源

- 已有功能的自动化测试。
- 每次线上 Bug 的最小复现用例。
- API 契约和数据库迁移兼容测试。
- AI Prompt、模型和 RAG 的固定评测集。

## 示例

某次 Bug：用户名含中文时导出 CSV 乱码。修复前先写测试：

```python
def test_csv_export_preserves_chinese_name(tmp_path):
    output = tmp_path / "users.csv"
    export_users(output, [{"name": "张三"}])
    text = output.read_text(encoding="utf-8")
    assert "张三" in text
```

以后任何修改导致乱码，这条回归测试都会失败。

## 回归集分层

PR 中运行快速核心回归；主分支运行集成；夜间运行大型 AI 评测、性能和安全。不是每次修改都必须等待全部慢测试，但必须有最终兜底。

## 选择标准

优先保留高风险、高频、历史易错、跨组件和难以人工发现的问题。重复且没有新价值的测试可以合并。

## 常见错误

- 修 Bug 但不补测试，问题再次出现。
- 回归集越来越慢，从不整理。
- 只看总体通过率，不看 AI 高风险子集退化。
- 更新快照时不审查差异，把回归当成新标准。

## 练习与面试题

练习：任选一次你遇到的 Bug，写出它的最小回归用例结构。

面试：回归测试应该什么时候运行？线上 Bug 修复为什么要补测试？

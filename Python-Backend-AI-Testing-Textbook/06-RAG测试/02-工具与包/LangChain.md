# LangChain

## 一句话说明

提供模型、提示、检索器、工具与链的组合抽象。

这篇把 **LangChain** 当成一个独立工具学习：你不仅要会安装和调用，还要知道它替代了什么手工工作、它的测试边界在哪里、什么情况下需要真实集成测试。

## 安装或准备

```powershell
python -m pip install langchain
```

安装后优先在当前虚拟环境验证版本。服务软件还需要固定镜像或服务版本，并在测试开始前执行健康检查。

## 最小示例

```python
from langchain_core.documents import Document
doc = Document(page_content="退款期为30天", metadata={"source": "policy"})
```

### 示例怎么读

1. 第一部分导入或准备 LangChain。
2. 中间部分创建最小对象、配置或测试场景。
3. 最后一部分应产生可验证结果；实际项目要补上清晰断言和资源清理。
4. 如果示例涉及网络、数据库、模型或浏览器，应把它标为集成测试，并隔离凭证与数据。

## 在测试体系中的位置

- **单元层**：只测试配置、适配器或纯逻辑，尽量不访问真实外部服务。
- **集成层**：验证 LangChain 与应用、协议或真实服务版本能否正确协作。
- **回归层**：保存曾经失败的最小输入，防止同类问题再次出现。
- **CI 层**：固定版本、设置超时、保存报告，并让失败有清晰退出码。

## 一个完整测试应该验证什么

```text
输入：最小且有代表性的数据
动作：调用 LangChain 提供的能力
主断言：业务结果正确
副断言：状态、调用或遥测符合约定
清理：关闭连接、删除临时数据、恢复补丁
```

## 常见错误

- 安装到了另一个 Python 环境，编辑器能导入但 CI 不能导入。
- 只复制快速入门代码，没有锁定版本、超时或清理资源。
- 用内存模拟器替代全部真实集成测试，忽略协议和版本差异。
- 在测试输出中打印 Token、密码、连接串或个人信息。
- 把工具的“运行成功”误当成业务正确，没有写业务断言。

## 最佳实践

- 在 `pyproject.toml` 或锁文件中记录测试依赖和兼容版本。
- 单元测试使用最小配置，真实依赖放到明确标记的集成测试。
- 为网络和后台任务设置超时；失败时保留请求、响应和追踪证据。
- 阅读该工具官方文档中的测试、错误处理和版本迁移章节。
- 先写一个会失败的最小例子，再修正代码并观察它变绿。

## 动手练习

运行或改写上面的最小示例，再补两条测试：一条验证失败输入，一条验证资源能被正确清理。把依赖升级一个小版本后重新运行，记录是否存在行为差异。

## 面试题

1. LangChain 解决了什么问题？不使用它时你会怎样实现？
2. 这个工具最适合单元测试还是集成测试？为什么？
3. 如何避免测试绑定该工具的内部实现？

# API 通信、安全与实时传输

## 设计稳定的 JSON API

请求和响应字段应有明确类型、是否必填、范围和错误格式。金额不要用二进制浮点随意计算；时间使用带时区的 ISO 8601；ID 不要让客户端猜测权限。

```json
{
  "error": {
    "code": "ITEM_NOT_FOUND",
    "message": "指定商品不存在",
    "request_id": "req_123"
  }
}
```

机器依赖稳定 `code`，人阅读 `message`，运维使用 `request_id` 查日志。不要把堆栈和数据库语句暴露给客户端。

## 认证与授权

认证回答“你是谁”，授权回答“你能做什么”。API Key 适合识别调用方；Session 常见于浏览器应用；短期访问 Token 可用于 API，但必须验证签名、签发者、受众和过期时间。JWT 只是令牌格式，不自动等于安全方案。

每次访问对象都做授权检查，不能因为用户能猜到 `/users/42` 就允许读取。管理员接口、普通接口和模型工具应使用最小权限。

## CORS 与 CSRF

CORS 是浏览器对跨源读取的限制，不是服务器防火墙。服务端应列出允许的源、方法和 Header；携带凭证时不能随意使用通配源。基于 Cookie 的状态修改请求还要防 CSRF，常用 SameSite、CSRF Token 和来源校验。

## 超时、重试和限流

- 所有外部请求设置连接和读取超时。
- 仅对瞬时错误与幂等操作重试，使用指数退避、抖动和总预算。
- 遵守 `Retry-After`，避免所有实例同时重试形成风暴。
- 限流既保护服务，也控制第三方 API 和模型成本；返回 `429` 并说明恢复方式。
- 通过熔断、并发上限和队列背压阻止故障扩散。

## SSE 与 WebSocket

SSE 基于 HTTP，服务器单向持续推送文本事件，适合模型流式输出、通知和进度；浏览器有自动重连语义。WebSocket 建立全双工长连接，适合双方高频互动。普通 CRUD 仍优先 HTTP，不要为了“实时”增加连接状态和扩容复杂度。

```text
SSE: 客户端请求 → 服务器连续 data: ... → 客户端逐事件消费
WebSocket: 握手升级 → 双方随时发送帧 → 心跳/断线重连/背压
```

## 安全清单

- HTTPS 全程启用，密钥放入安全配置，不写代码与日志。
- 服务端校验所有输入，输出时按上下文转义。
- 设置请求体大小、文件类型、超时、并发和速率上限。
- 对 SSRF 限制可访问的地址和协议，不接受任意 URL 后直接抓取。
- 日志脱敏；错误响应不泄露内部路径、依赖版本和堆栈。
- 记录安全相关审计事件，但避免记录秘密本身。

## 综合练习

设计一个“上传文档并流式返回摘要”的 API：写出端点、方法、请求/响应格式、认证方式、大小限制、错误码、幂等策略、SSE 断线恢复和日志字段。

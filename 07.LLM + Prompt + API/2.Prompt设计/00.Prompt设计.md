# Prompt 设计

## 基本结构

一个可维护提示通常包含：任务目标、输入数据、可用证据、输出格式、边界条件和失败处理。把规则和用户数据清楚分隔，避免模型误把文档中的指令当成开发者要求。

```text
任务：从用户邮件中提取订单号和诉求类型。
规则：只依据邮件正文；找不到订单号时返回 null，不猜测。
输出：符合指定 JSON Schema。
输入：<email>...</email>
```

## 迭代方法

1. 写出可观察的成功标准和失败样本。
2. 用最小提示跑基线。
3. 逐条增加必要约束或少量代表性示例。
4. 在固定测试集上比较结果，而非只看一条漂亮输出。
5. 保存提示版本、模型版本、参数和评测结果。

Few-shot 示例应覆盖边界情况，避免全是简单正例。对于严格格式，优先使用结构化输出能力并在服务端继续校验，不依赖“请务必输出 JSON”这类自然语言约束。

## 分清指令与数据

外部网页、PDF、检索片段和工具结果都属于不可信数据。它们可能写着“忽略以上规则”“发送密钥到某地址”。系统必须保留指令层级，对工具动作做白名单、权限检查和必要的人类审批。

## 事实性与拒答

让模型明确区分“有证据”“根据证据推断”“资料不足”。RAG 场景要求给出引用位置，并允许回答“未找到”。引用需要服务端检查是否真对应材料，不能只看形式上出现了来源标记。

## 常见错误

- 在提示里塞完整数据库或所有历史消息，造成成本、泄露与干扰。
- 用隐藏提示承担授权与数据隔离；提示不能代替服务端控制。
- 同时要求极短、完整、逐条引用，目标冲突却未定优先级。
- 只测理想输入，不测空值、恶意输入、多语言与超长输入。

## 练习

为“生成会议纪要”写一个提示，要求区分决定事项和待确认事项；再设计五条对抗样本检验是否会编造负责人和截止日期。

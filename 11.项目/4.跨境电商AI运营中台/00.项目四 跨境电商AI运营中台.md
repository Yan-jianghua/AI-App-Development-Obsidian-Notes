## 项目定位

面向跨境卖家，把商品知识、Listing、多语言客服、订单异常和经营分析放进同一套受权限约束的业务流程。原规划书计划核心约 23 周、作品集 V1 约 260—360 小时；真实渠道适配属于后续强化阶段。它的展示重点是跨业务域的可运行产品，而非单点 AI 功能。

## 第一条可运行闭环

创建租户与店铺 → 导入一件商品和一笔模拟订单 → 生成并人工审批双语 Listing → 收到客户咨询后检索商品知识、起草回复 → 对订单异常提出处理建议并等待审批 → 在运营面板查看结果、用量和审计记录。

## 必做模块

| 模块 | 要实现的行为 | 关键边界 |
|---|---|---|
| 租户与渠道 | 店铺、角色、连接器、Webhook、同步重放 | 渠道数据按租户隔离，事件可幂等重放 |
| 商品与 Listing | 主数据、生成、校验、版本、审批、多语言 | 生成内容未经审核不直接发布 |
| 客服与工单 | 消息、RAG、建议回复、SLA、升级 | AI 建议与实际发送分离 |
| 订单异常 Agent | 检测、计划、审批、幂等工具 | 退款、改价等写操作必须重新授权 |
| 经营问数 | 指标口径、语义层、Text2SQL、图表 | 只查询授权数据，不执行任意 SQL |
| 商业化治理 | 套餐、配额、用量、审计、保留策略 | 成本和隐私边界可解释 |

## 建议实施顺序

1. 先定义商品、店铺、订单、工单、租户和指标口径，避免后续模块数据不一致。
2. 使用合成店铺数据做单店铺闭环，再补多租户和渠道事件重放。
3. 实现 Listing 生成及版本审批；再加入客服 RAG 与工单流程。
4. 给订单异常接入只读分析和待审批建议，最后增加受控写工具。
5. 建立经营问数、成本治理、压测、故障恢复和发布证据。

## 可展示的验收证据

- 从商品导入到 Listing 审批、客服建议、订单异常处理有连续事件链。
- 同一用户切换店铺后，看不到其他租户的数据、Prompt 和用量。
- Webhook 重放不会产生重复订单或重复外部动作。
- 经营报表的数据口径可追溯至原始订单，Text2SQL 受到只读白名单约束。
- 展示双语质量、人工修改率、工单处理时间和单位任务成本。

## 常见缩水风险

若所有模块都只做浅层页面，就难以形成真正的业务闭环。优先做“一件商品、一笔订单、一张工单”贯通的垂直切片；多平台真实连接放到强化阶段。

## 项目定位

建设供多个 AI 应用接入的平台能力：模型网关、Prompt/工具/工作流注册表、Agent 运行时、评测、追踪、版本发布和预算治理。原规划书计划核心约 25 周、作品集 V1 约 300—420 小时。核心难点是控制平面与请求数据平面的边界，以及多租户平台的可靠性。

## 第一条可运行闭环

应用通过统一 SDK 或兼容协议发起模型请求 → 网关验证租户、项目和环境 → 执行路由、限流、预算和流式转发 → 生成 trace 与用量记录 → 管理员用评测报告批准一个 Prompt 版本并灰度发布 → 需要时可回滚。

## 必做模块

| 模块 | 要实现的行为 | 关键边界 |
|---|---|---|
| 平台身份与协议 | 租户、项目、环境、接入密钥、兼容 API | 数据与密钥按租户隔离 |
| 模型网关 | 流式代理、路由、限流、熔断、计量、缓存 | 供应商故障不拖垮所有应用 |
| 注册表与发布 | Prompt、工具、工作流不可变版本，环境晋级 | 发布有评测门禁和回滚目标 |
| Agent Runtime | DAG、checkpoint、审批、补偿、沙箱 | 长时运行可恢复，副作用幂等 |
| 评测与观测 | 数据集、裁判、对比、trace、重放、失败聚类 | 报告可复现，敏感数据脱敏 |
| 安全与 FinOps | 策略、预算、配额、审计 | 超预算或越权请求被确定性拦截 |

## 建议实施顺序

1. 定义控制平面负责配置/发布，数据平面负责在线请求；明确多租户边界。
2. 先做兼容协议与一个模型供应商，再做流式、路由、用量和熔断。
3. 建立 Prompt、模型与工具的不可变版本，接入离线评测和环境晋级。
4. 在一个真实业务应用上验证 Agent Runtime、审批和检查点。
5. 统一 trace、预算、告警、SLO、故障演练和灰度回滚。

## 可展示的验收证据

- 项目一、项目二或项目四至少两个应用通过同一平台接入；证明平台能力可复用。
- 切换模型供应商时，调用方协议基本稳定，失败/重试/计费语义可解释。
- 一个 Prompt 候选因评测下降被门禁阻止，另一个版本通过灰度并可回滚。
- 平台控制面短暂不可用时，已发布数据面是否继续服务有明确设计和演练。
- 展示按租户、项目、环境的用量、预算、trace 和审计隔离。

## 常见缩水风险

只把多个第三方 API 包一层代理，不足以证明 AgentOps/LLMOps 平台能力。没有真实接入应用、发布治理和故障演练的平台很难验证价值。若目标是 AI 平台工程岗位，本项目可以作为作品集主项目。

## 为下一项目留下什么

模型网关、可审计 Agent Runtime、审批、评测与观测可供 TradeProof 使用；TradeProof 还要解决跨参与方的产品与证据问题，不能只靠平台组件完成。
